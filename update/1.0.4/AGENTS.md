# SPEC — модуль `awz.allxls` (v1.0.2)

Спецификация модуля «Пошаговый импорт/экспорт XLSX/CSV» для Bitrix. Файл подключается в каждую сессию работы по модулю — держи актуальным при изменениях.

## Cron-запуск по расписанию
- Два способа запуска: **агент Bitrix** (`Awz\Allxls\Cron\Agents::runAll`, периодический, интервал 300 сек, регистрируется в `createAgents` инсталлера, `lib/cron/agents.php`) и **CLI-точка входа** `cron/run.php` (только CLI, URL-запросы отклоняются): `php cron/run.php all` — **общее cron задание**, только профили с `CRON_ACTIVE=Y` и `SETTINGS[CRON_MODE]='cron'`; `php cron/run.php 3,7` — **отдельные cron задания**, скрипт проверяет опцию в профиле: требуется `CRON_ACTIVE=Y` и `CRON_MODE='cron_own'` (иначе skip «способ запуска... запрещен»), накопленное расписание не учитывается (кроме `CRON_PAUSE`). Аргумент `-t N`/`--time=N` или env `AWZ_ALLXLS_TIME_LIMIT` — таймаут работы скрипта в секундах (0/не задан — без ограничения; не начатые профили пропускаются, текущий профиль ограничен остатком времени через `Runner::setTimeLimit` → дедлайн в `exec` и `$runTimeLimit` в `runController`)
- CLI-точка входа также принимает `-t N`/`--time=N` или env `AWZ_ALLXLS_TIME_LIMIT` — таймаут работы скрипта, сек (0 — без ограничения): не начатые профили пропускаются (status `skip`), текущий профиль ограничен остатком времени (`Runner::setTimeLimit` → дедлайн в `exec` и `$runTimeLimit` в `runController`)
- Режимы прогона (колонка `CRON_HIT_TIME`): `0` — профиль обрабатывается целиком за один вызов (хиты по `HIT_TIME_LIMIT=300` сек до `done`); `>0` — **пошаговый режим по времени**: за один вызов не более `CRON_HIT_TIME` сек (например 20 сек), остальное — на следующем вызове агента/crontab (`DATE_NEXT_RUN` не продвигается до завершения, `RUN_COUNT`/`DATE_LAST_END` — только по факту `done`)
- Пауза после завершения (колонка `CRON_PAUSE`, сек, 0 — выключено; задается на шаге 4 рядом с «Время одного шага», экшен `cronsave` параметр `pause`): после `done` `DATE_NEXT_RUN = max(расписание, done + CRON_PAUSE)`; проверка `DATE_NEXT_RUN` действует и для явного запуска по списку ID (если `CRON_PAUSE>0` — skip с сообщением «пауза после завершения (до #DATE#)», иначе явный запуск — вне очереди). Сценарий: crontab каждые 5 минут `run.php <id>` + пошаговый режим + пауза 2 часа. `cronsave` при `release=Y` настройки (CRON_ACTIVE/HIT_TIME/PAUSE) не перезаписывает
- `lib/cron/schedule.php` (`Awz\Allxls\Cron\Schedule`): парсер crontab-выражений (5 полей, `*`, списки, диапазоны, шаги, алиасы @hourly/@daily/@weekly/@monthly/@yearly), `validate`, `getNextRun(expr, from)`
- `lib/cron/runner.php` (`Awz\Allxls\Cron\Runner`): на каждый профиль — блокировка в БД в записи профиля (`CRON_RUNNING='Y'` + `CRON_START_TIME`; атомарный `UPDATE ... WHERE CRON_RUNNING<>'Y'`), блокировка старше 12 часов (`LOCK_TIMEOUT`) автоматически снимается; `isProfileLocked` (используется для запрета редактирования), `releaseLock`, `ensureColumns` (ленивая миграция колонок)
- Прогон: контроллеры вызываются напрямую (`Pimport::importAction` / `Pexport::exportAction` с `fromCron='Y'`, хиты по `HIT_TIME_LIMIT=300` сек) в цикле до `done`; ВАЖНО: каждый вызов cron создает новый контроллер — `reset='Y'` только если состояние нового прогона (`PROCESS.DONE='Y'` или `PROCESSED=0`), иначе `reset='N'` (продолжение с курсора; раньше каждый cron-вызов сбрасывал состояние и перечитывал файл с начала); лимиты `RUN_TIME_LIMIT=21600` сек и `MAX_ITERATIONS=5000`. По завершении: `DATE_LAST_END`, `RUN_COUNT++`, `DATE_NEXT_RUN` из расписания, `CRON_LAST_ERR` (при ошибке), снятие блокировки. Для `all`-прогонов запуск строго по `DATE_NEXT_RUN`; явный список ID — вне очереди
- `Pimport::importAction`/`saveParamsAction`, `Pexport::exportAction` и `Profiles::saveAction`/`saveFileAction`/`saveSettingsAction` при активной блокировке (`CRON_RUNNING`) возвращают ошибку `CRON_RUNNING` — cron-процесс проходит с `fromCron='Y'`; `Pimport::finishAction` (кнопка «Завершить обработку») вместо блокировки снимает cron-блокировку (`Runner::releaseLock`) и завершает импорт
- Способ запуска **per-profile** `SETTINGS['CRON_MODE']` ('cron' — общее cron задание | 'cron_own' — отдельное cron задание | 'agent', по умолчанию 'agent' — cron по умолчанию выключен; летучий ключ — на SETTINGS_HASH не влияет; задается на шаге 4, `cronsave` параметр `mode`): `Runner::execAll(string $mode='')` фильтрует профили по способу: агент (`Agents::runAll`) → `execAll('agent')`, `cron/run.php all` → `execAll('cron')`; `run.php <id>` (explicit) — только `CRON_MODE='cron_own'` (проверка в `Runner::runProfile`, lang `AWZ_ALLXLS_CRON_RUN_WRONG_MODE`). В UI статуса для режима «агент» показывается статус агента (`Agents::status()`: exists/active/duplicates/next_exec/overdue, отставание `CRON_OVERDUE_SEC=600` сек) с предупреждениями о падениях/дубликатах
- Админка (шаг 4, блок «Расписание запуска (cron)»): **простой режим** — переключатель запуска + способ запуска (crontab — рекомендуется / агент Bitrix) + готовые интервалы (5/15/30 мин, 1/2/6/12 час, ежедневно/еженедельно/ежемесячно → генерируют crontab-выражение) + «Время одного шага запуска» (0 — до завершения / 20 сек / 1 мин...); **экспертный режим** (скрывается/показывается переключателем, состояние в localStorage) — ввод `CRON_SCHEDULE` вручную (валидация на сервере), рекомендуемая команда crontab `*/3 * * * * php .../cron/run.php all` (раз в 3 минуты, все профили в режиме crontab). Статус (выполняется/следующий запуск/последняя ошибка/способ запуска/статус агента), кнопка «Снять блокировку». Экшены: `awz:allxls.api.profiles.cronsave` / `.cronstatus`. На шагах 1–4 при активном запуске показывается баннер, редактирование профиля (шаги 1–3 и параметры шага 4) заблокировано до завершения
- Колонки `b_awz_allxls_profiles`: `CRON_ACTIVE`, `CRON_SCHEDULE`, `CRON_HIT_TIME`, `CRON_PAUSE`, `CRON_RUNNING`, `CRON_START_TIME`, `CRON_LAST_ERR` + индекс `(CRON_ACTIVE, DATE_NEXT_RUN)`; миграция в `checkOldInstallTables` (install/index.php) и лениво через `Runner::ensureColumns`

## Назначение
Импорт и экспорт данных (XLSX/CSV/XML/YML/JSON) в сущности Bitrix (сейчас — инфоблоки) через пошаговый мастер в админке с профилями, разделами профилей, правилами сопоставления колонок и собственной системой прав.

## Ключевые классы
### ORM (`Awz\Allxls\Tables`)
- `ProfilesTable` — события onBeforeAdd/Update/Delete проверяют права через `AccessController::can(...)`; `prepareUpdateFields` автозаполняет DATE_UPDATE/UPDATED_BY и пересчитывает `SETTINGS_HASH` (md5 от JSON с рекурсивной сортировкой ключей; «летучие» ключи `PROCESS`, `HIT_TIME_LIMIT`, `MAX_EXECUTION_TIME`, `LOG_ERRORS`, `HASH_TYPE`, `HASH_MEM_CACHE`, `HASH_USED_COLUMNS`, `STEP_BY_STEP` исключаются); смена хеша → `ProfilesHashesTable::clearProfileHashes()`
- `SectionsTable` — запрет удаления раздела с профилями
- `ProfilesHashesTable` — `checkRowHash`, `saveRowHash(profileId, rowHash, elementId='', entityId='')`, `deleteRowHash(profileId, rowHash)`, `loadRowHashes(profileId)` (все пары ROW_HASH => ELEMENT_ID актуального SETTINGS_HASH одним запросом — для опции HASH_MEM_CACHE; ELEMENT_ID нужен Pimport для определения финальности хеша), `getProfileSettingsHash` (кеш на процесс), `clearProfileHashes`, `clearElementHashes(elementId, entityId='')`; ELEMENT_ID (varchar)/ENTITY_ID заполняются при импорте и используются для сброса хешей при внешнем изменении/удалении элемента
- `AdminPages\{ProfilesList, ProfilesEdit, SectionsList, SectionsEdit}` — НЕ ORM; классы админ-страниц поверх `Awz\Admin\IList/IForm`; статические `getTitle()`, `getParams()`; мастер ProfilesEdit = 4 шага (шаблоны `tables/adminpages/templates/profilesedit/step*.php` + `script*.php`)

### REST-контроллеры (`Awz\Allxls\Api`, маршруты `awz:allxls.api.<controller>.<action>`, BX.ajax.runAction)
Prefilters: `Authentication` + `CloseSession`.
- `Profiles` (api/profiles.php) — мастер: `saveAction` (шаг 1: NAME/ACTIVE/SECTION_ID/DESC/TYPE), `saveFileAction` (шаг 2: FILE_PATH/PROXY/CSV_DELIMITER/CSV_ENCODING, DEST_TYPE=`iblock|orm`, IBLOCK_ID/ORM_FILE, MAX_PARAMS — макс. количество колонок (параметров) из файла импорта в настройках шага 3 (колонки сверх лимита не показываются и не сохраняются, `Profiles::settingsAction` отсекает COLUMNS листов), по умолчанию 0 — без ограничения; для XML/YML/JSON-источника обязателен `XML_PATHS` — пути до элементов, сохраняется разобранным массивом [['PATH','SEGMENTS'],...]), `settingsAction` (шаг 3 чтение: заголовок + 20 сэмплов через FastXlsReader/CSV; для xml/yml — `buildXmlSheets` по XML_PATHS; для json — `buildJsonSheets` по XML_PATHS), `saveSettingsAction` (шаг 3 запись: SHEETS[SHEETn]={NAME,ACTIVE,HEADER_ROW,COLUMNS[col_N]={INCLUDE,ALIAS,LETTER,HEADER,MAPS[],MAP_SETTINGS[]},...}), `fieldsAction` (поля назначения)
- `Pimport` (api/pimport.php) — импорт: `importAction(id, hitTimeLimit, maxExecutionTime, reset, logErrors)` — цикл `importStep()` внутри хита; курсор (лист/строка) в `SETTINGS['PROCESS']`. `MAX_EXECUTION_TIME` в UI не задается (сервер сам считает лимит из hitTimeLimit+10); пауза между запросами `REQUEST_DELAY` (сек, по умолчанию 0) задается на шаге 4 и применяется в JS (`tickDelayed`, watchdog учитывает `tickPending`). CSV — запись-ориентированное чтение `fgetcsv` (позиционирование по номеру записи, заголовок HEADER_ROW пропускается каждый хит; байтовые смещения CCSVData сломаны на многострочных полях в кавычках; при OFFSET>0 в состоянии — миграция: сброс курсора на начало). CSV-хэндл и промотка кешируются на хит (свойства `csvHandle`/`csvSkipPending`), повторное чтение ошибочной строки в рамках хита — из буфера `csvPendingRow` (актуально и для XLSX); профиль читается один раз за хит (`profileHitCache`). XLSX — состояние FastXlsReader. XML/YML — состояние FastXmlReader (`fastXmlReader` на хит; выравнивание строк по `sheetXmlKeys` (HEADER колонок); HEADER_ROW игнорируется — первый элемент листа = строка 1; лист = путь из `XML_PATHS`, коды SHEETn в порядке путей). JSON — состояние FastJsonReader (`fastJsonReader` на хит, тот же контракт, что у XML: лист = путь из `XML_PATHS`, выравнивание по `sheetXmlKeys`, HEADER_ROW игнорируется, байтовый курсор в `PROCESS.XML_POS`; поддерживаются `{"items":{"item":[..]}}`, `{"items":[..]}` (элементы массива — строки листа) и корневые массивы; скалярные элементы листа (массив скаляров) дают курсор после значения — валидация позиции ('}'/']'/после строки) не проходит и выполняется фолбэк-промотка сканером от начала). Рабочая копия файла источника: на старте импорта файл копируется в `/upload/tmp/awz.allxls/` (`PROCESS.TMP_FILE`, `ensureSourceCopy`, `Bitrix\Main\IO\File`), читается снимок (живой файл может измениться и дать артефакты), по завершении (`done`)/`finishAction`/`resetState` копия удаляется; пропавшая копия пересоздается. `getTotalRows` при импорте НЕ пересчитывается на каждый хит: итоговое количество строк листа берется из состояния `SHEET_TOTALS` (файл — снимок, стабилен), полный скан выполняется только при первом чтении листа — иначе на больших XML время хита уходило на повторный скан и хиты падали по `max_execution_time`. Байтовый курсор XML-листа (`PROCESS.XML_POS`, как у CSV, `FastXmlReader::scanItemEnd`): после каждого прочитанного элемента листа запоминается байтовая позиция файла сразу после его закрывающего тега (например после `</offer>`) — ищется строковым лексером (UTF-8 файлы; CDATA/комментарии пропускаются, одноименная вложенность и родители пути учитываются через сеяный родительский стек), хранится в состоянии `state['bytePos']` и коммитится в `PROCESS.XML_POS` только при сдвиге курсора строки (успех/пропуск; при ретрай-ошибке — не коммитится, строка перечитывается с прежней позиции). Для не-UTF-8 файлов — фолбэк на seek-промотку от начала файла (байтовый курсор не пишется). Следующий хит: reader открывается сразу на сохраненной позиции через stream-wrapper `awzseek://offset|path`, промотка с начала не выполняется; позиция валидируется (последний байт — `>`, за пределами файла — чтение завершено). Устойчив к обрывам: защитный запас 2 сек до конца хита перед строкой, резерв хеша строки ДО обработки, снятие резерва и ретрай до 3 попыток при ошибке (PROCESS.RETRY). «Висячие» резервы (хеш с пустым ELEMENT_ID после обрыва хита до создания элемента) не пропускаются по хешу — `isHashFinal` требует непустой ELEMENT_ID или маркер `HASH_SKIP_MARK='skip'` (строки, пропущенные по правилам), иначе резерв снимается и строка обрабатывается повторно (поиск элемента идемпотентен). Режим «импорт по одному элементу» — опция `STEP_BY_STEP` финального этапа (сохраняется в `saveParamsAction`): `importAction` обрабатывает одну строку за запрос и останавливается, следующий элемент — кнопка «Следующий элемент» (JS `profiles_edit_step4.js`, флаг UI `awz_allxls_profile_process_step_by_step`). Ответ `importAction` дополнительно содержит `debug` (только в режиме `STEP_BY_STEP`: лист/строка, значения колонок из файла `raw` (с финальным значением каждой колонки — `cols` по ключам колонок, собранным в `buildItem` (mode=all); при пропуске — причина `skip_type`, при skip-правиле колонки без результата помечены «Пропуск строки»), сработавшие правила `rules` — статический коллектор `MapRules::$lastApplied` сбрасывается перед сборкой элемента, причина пропуска `skip_rule/skip_value`), а `item.debug` — режим обработки (`new|update`) и фильтр поиска элемента; UI выводит блок «Техническая информация». Дедуп может работать «все хеши в память» — опция `HASH_MEM_CACHE` (Y: один SELECT на хит через `ProfilesHashesTable::loadRowHashes`, карта в памяти `hashMemSet` (ROW_HASH => ELEMENT_ID), синхронизируется в save/deleteHashSafe; N: запрос на строку), выбирается на шаге 4, сохраняется в `saveParamsAction`. Опция `HASH_USED_COLUMNS` (шаг 4, летучий ключ): `rowHashRaw` считается только по задействованным колонкам (INCLUDE=Y и есть сопоставления — `usedRowHash`), изменения неиспользуемых ячеек файла не вызывают повторный импорт; item-хеш не зависит от опции. Правило `TYPE=delete` («Удалить элемент», Map::getRuleTypes): `MapRules::processRules` ставит skip + флаг `MapRules::LastDelete`, `Pimport::rowDeleteRules` (сбрасывается в importStep); после сборки item и вычисления itemHash вызывается `deleteRowByRule`: buildItem(mode=search) -> buildFilter -> findElement -> `Services\iblock::deleteElement` (замер времени в импорт-классе, `svcTimeStats[delete]`) в обёртке `Handlers::withImportFlag` (событиям запрещено трогать хеши), оба хеша сохраняются с маркером `HASH_SKIP_MARK` (строка больше не обрабатывается); статистика «Удалено по правилу»/«Ошибки удаления по правилу» (importAction stats + finishAction STATS_VIEW), при неудаче — «Ошибки удаления по правилу» (не фатально, курсор сдвигается). ### Движок правил (`Awz\Allxls\MapRules`, lib/maprules.php)
Статический (docblock описывает полный формат SETTINGS.SHEETS[sheet].COLUMNS[from].MAP_SETTINGS[key]). Применяется в `Pimport::applyMaps`: `applyMaps($value,$col,$rowValues,$options)` — TRIM/CASE/REPLACE → правила TYPE=transform/skip/delete/unset/entity с CONDITIONS (AND/OR/AND_NOT/OR_NOT, CHILDREN, SOURCE/OP/VALUE/VALUE2) → SKIP_EMPTY; `processRules` → `{value, skip, unset}`; `evalConditions` (рекурсия CHILDREN); `checkCondition` / `checkOperator`; `applyAction` (replace, del_substr, replace_substr, prepend, append, lower, upper, firstupper, translit, unique_code→`Helper\Iblock::generateUniqueCode`, round, mul, div, add, sub, inc_percent, dec_percent, formula, build_json — финальное значение-JSON из шаблона (aval, макросы подставляются рекурсивно в строковые значения шаблона)); `expandMacros` (#VALUE# — начальное значение колонки-источника до правил (фиксируется в processRules через `options['initial_value']`), #VALUE_PROCESSED# — текущее обработанное значение цепочки правил, #ENTITY#, #COL_KEY# — начальное значение колонки, #COL_PROCESSED_KEY# — преобразованное значение колонки (лениво через getProcessedColumnValue с кешем строки), #ALIAS#, #ENTITY_<ПОЛЕ># — значение поля найденного элемента (options.entity_data, processItem после поиска; PROPERTY_XXX_VALUE поддерживается; в полной сборке — пусто)). Флаг пропуска: `public static bool $lastSkip = false;` — сбрасывается `Pimport::importStep` перед `buildItem` (`MapRules::$lastSkip = false`), проверяется после для решения о пропуске строки. Правило TYPE=unset («Не обрабатывать значение»): выставляет `MapRules::$lastUnset` — поле исключается из элемента (`buildItem` не пишет его в `$item`, строка обрабатывается штатно), статика сбрасывается в обёртке `Pimport::applyMaps` перед каждым полем и в importStep/processItem; в `Map::getRuleTypes`/`getRuleControlId` ('ruleUnset')/`buildCondRules` (правило 2c), JS `controlIdMap` и whitelist шага 3 дополнены 'unset'. Правило TYPE=delete выставляет ОБА флага: `lastDelete` И `lastSkip` — поэтому в `Pimport::importStep` (обе ветки: XLSX/XML и CSV) проверка `rowDeleteRules` выполняется ПЕРВОЙ, до `rowSkipRules` (иначе delete-правило недостижимо и строка просто пропускается как «Пропущено по правилам»). `deleteRowByRule` ищет элемент через buildItem в режиме `search` (только поля-фильтры) и удаляет через `svc deleteElement`, сохраняет хеш строки с маркером HASH_SKIP_MARK (строка не обрабатывается повторно), в статистику идут удаленные элементы; при отсутствии элемента — удаление не выполняется, строка обрабатывается штатно.

### Хелперы (`Awz\Allxls\Helper`)
- `FastXlsReader` — потоковый XLSX-ридер (ZipArchive + XMLReader по `zip://...#xl/worksheets/sheetN.xml`): `getSheets`, `getSheetIndexByName`, `getTotalRows`, `readRow`, `readNextRow`, `readSheetsHead`, `openSheet`, `readRows`, `getState/setState`, `close`. ВАЖНО: после `openSheet()/fastForward()` reader стоит на элементе `<row>` первой непрочитанной строки — флаг `$atRowStart` гарантирует, что `readNextRow()`/`parseRows($atStart=true)` обрабатывают её без предварительного `read()` (иначе первая строка каждого хита молча терялась). Полностью пустые строки в XML отсутствуют — `readNextRow` возвращает фактический номер (`r`), «дыры» между строками — это отсутствующие в файле строки
- `FastXmlReader` (`lib/helper/fastxmlreader.php`) — потоковый XML/YML-ридер (XMLReader, побайтово; не-UTF-8 кодировки конвертируются iconv-фильтром по `encoding=` из декларации). «Лист» — путь до повторяющегося элемента произвольной глубины (`XML_PATHS`: 'items->item', 'shop->offers->offer'; разделители списка — запятая/`;`/перевод строки, в пути — `->` или `/`); матчится по суффиксу стека тегов (работает под любым корнем). API зеркален FastXlsReader: `getSheets`, `getSheetIndexByName`, `getTotalRows` (полный скан-подсчет, кеш), `setKeys` (порядок ключей для выравнивания строк под колонки листа), `readSheetsHead($maxItems)` (шапка = union ключей первых N элементов; ROWS[1] — ключи, 2..N — данные), `openSheet/readNextRow/getState/setState/close` (`lastRow` = число потребленных элементов листа; `bytePos` = байтовая позиция курсора — байт сразу после закрывающего тега последнего обработанного элемента, между хитами чтение продолжается с нее без промотки; для не-UTF-8 файлов — промотка seek-ом от начала). Колонки строки: тег → ключ с транслит-именем; атрибуты → `тег_атрибут` (имя атрибута сохраняется как в XML: `<category id="111474" parentId="30149">` → `category_id`, `category_parentId`); спецкейс атрибут `name` — его ЗНАЧЕНИЕ (транслит) формирует ключ: `<param name="длина">10</param>` → `param_dlina`; именованные вложенные элементы (атрибут name) формируют ключи от имени тега без префикса родителя: `<warehouse name="Самара" unit="шт">5</warehouse>` → `warehouse_samara` (текст), `warehouse_samara_unit` (атрибут) + общий ключ тега `warehouse` (значения склеены) + JSON-агрегат `warehouse_json` — `[{"name":"Самара","unit":"шт","value":5},...]` (по одному на каждый тег с name, значение value — числовое, если числовое); для тега `category` колонка `category_parentId` присутствует всегда (пусто, если атрибута нет); вложенные теги → `родитель_тег`; повторы склеиваются ", "; `ProfilesHelper::parseXmlPaths` / `buildXmlSheets` (шаг 3: HEADER_ROW всегда 1, листы SHEETn в порядке путей)
- `FastJsonReader` (`lib/helper/fastjsonreader.php`) — потоковый JSON-ридер (побайтовый собственный лексер-сканер по чанкам 256К, файл не грузится в память; сам элемент декодится штатным json_decode, cp1251 — фолбэк iconv). API полностью зеркален FastXmlReader (`getSheets/getSheetIndexByName/getTotalRows/setKeys/readSheetsHead/openSheet/readNextRow/getState/setState/close`, `bytePos`-курсор в состоянии). Пути `XML_PATHS` матчатся по суффиксу стека ключей; для JSON допустим ОДИН сегмент (`parseXmlPaths($raw, 1)` — `saveFileAction` использует min=1 при srcExt=json): товары в корне файла — `{"products":[...]}` (ключ-массив) или корневой массив `[{...},...]`/массив скаляров; поддерживаются: вложенный контейнер `{"shop":{"offers":{"offer":[...]}}}`, массив под родителем `{"items":[...]}` (каждый объект массива — строка листа), корневой массив `[{...},...]`, массив скаляров как лист (колонка = имя листового сегмента). Колонки: поле → ключ (lowercase, не-[A-Za-z0-9] → '_'); вложенный объект → `родитель_поле`; массив скаляров → склейка ", "; массив объектов → JSON-агрегат под ключом поля; null/bool → ''/'true'/'false'. Байтовый курсор — байт сразу после '}' элемента; JSON-структура ASCII-прозрачна (валидация позиции: предыдущий байт '}'/']'); возобновление — fseek + сеяный стек родителей пути (leafArray-фрейм: элементы массива = строки листа), без промотки. ### Логгер и обработчики (`Awz\Allxls`)
- Маркер cron-запуска в состоянии профиля: при CLI-вызове (`fromCron='Y'`) `Pimport` (свойство `isCronRun`, через `saveState`/`dumpLiveStats`) и `Pexport` пишут `PROCESS[SOURCE]='cron'`, heartbeat `PROCESS[CRON_ALIVE]` и `PROCESS[RUN_STARTED]` (старт прогона; общее время работы в UI при cron считается как elapsed от него, включая паузы между cron-вызовами) (unix ts, обновляется каждые 30 сек в долгом хите и в конце каждого cron-хита; переживает промежуточные `saveState` через keepKey); JS шага 4 (`profiles_edit_step4.js`/`_export.js`) при `SOURCE=cron` и `DONE!=Y` — а также по факту `running` из `cronstatus` (проверка при загрузке страницы, для старых прогонов без маркера) — вместо «Импорт был прерван...» показывает «Обработка запущена на crontab» и фоновым `setInterval` раз в 20 сек опрашивает `cronstatus` (обновляя статистику из `stats_view` и прогресс-бар), при `running=false` опрос останавливается
- Детект падения cron: `Runner::CRON_DEAD_AFTER=180` сек без heartbeat (`isCronAlive`) — cron считается упавшим; `Runner::runProfile` при мертвой блокировке снимает ее и продолжает обработку с места обрыва, инкрементируя `CRON_FALLS` (`registerCronFall`); при `CRON_FALLS > Runner::MAX_CRON_FALLS=10` — блокировка снимается, автопродолжение останавливается («превышен лимит подряд идущих падений cron-процесса»), счетчик сбрасывается при `done`. Ручные действия при живой блокировке: `cronRunGuard` (Pimport/Pexport) и `cronLockedGuard` (Profiles) блокируют с сообщением «подождите 3 минуты...», при мертвой — блокировка снимается и доступ разрешается; `Pimport::finishAction` при живой блокировке возвращает ошибку `CRON_ALIVE_WAIT` («подождите 3 минуты...»), при мертвой — снимает блокировку и завершает импорт
- «Живой» прогресс cron-запуска в UI: `Pimport::importAction` каждые 30 сек в рамках долгого хита делает `dumpLiveStats` (компактная `PROCESS.STATS_VIEW` в профиль, включая `RPS: среднее` и `RPS: последний хит`; `lastStatsView` имеет приоритет над кешем начала хита в `saveState` — иначе дамп затирался), `Pexport::exportAction` пишет `PROCESS_EXPORT.STATS_VIEW` на каждый хит; `cronstatus` возвращает `stats_view`, шаг 4 опрашивает его раз в 20 сек и при `running` показывает баннер «Обработка запущена на crontab» + прогресс-бар и таблицу статистики. Ресурсы БД: в cron `saveState` пишет состояние раз в 30 сек (`stateSaveInterval`, в браузере — 1 сек), дамп совмещен с записью состояния (без двойной записи)

## Конвенции кода
- Namespace: `Awz\Allxls\` + `\Api`, `\Tables`, `\Helper`, `\Services`, `\Access\{...}`. PSR-4 через автозагрузку Bitrix (lib/)
- Ядро: D7 (ORM, Engine\Controller, ServiceLocator, EventManager) для бизнес-логики; старое ядро (`\CIBlockElement`, админ-стиль) — для инфоблоков, админки. CSV читается только `fgetcsv` (не `\CCSVData` — у него ломается байтовый курсор на многострочных полях в кавычках)
- Lang: `Loc::loadMessages(__FILE__)`, файлы `lang/ru/<зеркало пути>`, ключи `AWZ_ALLXLS_<ПУТЬ>_<СМЫСЛ>`; в UI правил допустимы русские строки напрямую
- REST: ajax только через `BX.ajax.runAction`; ошибки — `$this->addError(new Error(...), 'UPPER_SNAKE_CODE')`
- Состояние импорта/экспорта — только в `SETTINGS.PROCESS` / `SETTINGS.PROCESS_EXPORT` (устойчиво к обрывам хита); служебные ключи не влияют на SETTINGS_HASH
- Дедуп импорта: хеши строк сохраняются только после успешной обработки; ITEM-хеш нестабилен при правилах, меняющих результат (unique_code) — строковый хеш проверяется всегда
- Фоновая вкладка браузера: цепочка хитов держится на watchdog в Web Worker (не троттлится), перезапуск только если ответов нет >15 сек (`lastActivity`) — исключены параллельные цепочки
- Тонкие admin-файлы (replace generator) — реальная логика в `Tables\AdminPages\*`
- Генерируемые блоки `/*awz.gen ... nodelete*/` в `lib/access/custom/*` — правки только вне блоков

## Известные особенности / техдолг
- `install/db/mysql/install.sql`: дублирующая колонка `DESC` в CREATE TABLE (строки 43, 46)
- `ProfilesTable::onBeforeUpdate/onBeforeDelete` для импорта по ошибке проверяет `ACTION_EXPORT_EDIT`/`ACTION_EXPORT_DELETE` (profiles.php:155, 180)
- Сохранение опций в options.php закомментировано
- `ProfilesHashesTable` кеширует SETTINGS_HASH профилей на процесс (сброс только через `clearProfileHashes`); `Services\iblock` кеширует свойства/enum/связи на процесс — при импорте несколькими процессами одновременно кеши независимы (корректно)
- Мастер ProfilesEdit (step4.js): watchdog импорта — Web Worker (Blob setInterval 5 сек) + фолбэк setInterval; флаг `inflight` + `lastActivity` против параллельных цепочек
